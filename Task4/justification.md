# Обоснование Terraform-конфигурации

В этом задании разворачивается одноузловой непроизводственный стенд. Он показывает автоматическое создание сети, правил доступа, вычислительного ресурса, системного и отдельного дисков, а также NAT. Стенд не выдаётся за production-вариант целевой платформы.

## Состав стенда

| Ресурс         | Конфигурация                                                    | Обоснование                                                                                                                                       |
| -------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| VPC Network    | Одна отдельная сеть                                             | Изолирует ресурсы задания от других облачных ресурсов и показывает базовую сетевую границу.                                                       |
| Subnet         | Одна подсеть `10.10.1.0/24` в одной зоне                        | Для одной VM нескольких подсетей не требуется. Диапазон оставляет достаточно адресов для дальнейшего увеличения стенда.                           |
| Security Group | SSH на порт 22 только с `admin_cidr`, исходящий трафик разрешён | VM доступна для администрирования, но прикладные порты не публикуются в интернет. Исходящий доступ нужен для установки пакетов и Docker-образов.  |
| Compute VM     | 2 vCPU, 4 ГиБ RAM, `core_fraction = 20`                         | Достаточно для проверки инфраструктуры и лёгкого демонстрационного сервиса. Полный набор Dremio, Airflow и DataHub на такой VM не предполагается. |
| Boot Disk      | 20 ГиБ `network-hdd`                                            | Достаточно для Ubuntu, Terraform не хранит на нём данные платформы. HDD дешевле SSD и приемлем для короткого учебного запуска.                    |
| Data Disk      | 30 ГиБ `network-hdd`                                            | Показывает разделение ОС и данных. Диск можно вручную смонтировать и использовать для демонстрационного MinIO.                                    |
| NAT            | Динамический публичный IPv4 на сетевом интерфейсе VM            | Даёт исходящий доступ и возможность SSH без отдельной NAT VM, Gateway. Для временного стенда постоянный IP не нужен.                              |

VM сделана прерываемой (`preemptible = true`), поскольку стенд нужен только на время `plan`, `apply`, проверки и создания скриншота. Это уменьшает учебные расходы.

## Почему один узел

Смысл задания — продемонстрировать воспроизводимое создание IaaS-ресурсов и их зависимостей. Разделение каждого продукта по отдельным VM, Kubernetes, балансировщик, несколько зон доступности и отдельный NAT Gateway заметно увеличили бы стоимость и объём конфигурации, но почти ничего не добавили бы к проверке Terraform.

Для production понадобятся private subnets, отказоустойчивость по нескольким зонам, резервное копирование, централизованный IAM, мониторинг и независимое масштабирование хранения и вычислений. Эти решения остаются частью целевой архитектуры, но осознанно не входят в учебный `apply`.

## Что автоматизировано, а что остаётся ручным

Terraform управляет:

- VPC и подсетью;
- Security Group;
- VM и её вычислительными параметрами;
- загрузочным и дополнительным дисками;
- подключением диска;
- динамическим внешним адресом через NAT;
- передачей открытого SSH-ключа в метаданные VM.

До запуска Terraform вручную подготавливаются Yandex Cloud CLI, временный IAM-токен, идентификаторы cloud/folder и локальная пара SSH-ключей. Секреты передаются провайдеру через `YC_TOKEN`, `YC_CLOUD_ID` и `YC_FOLDER_ID`, а не сохраняются в `terraform.tfvars`.

После `apply` вручную можно отформатировать и смонтировать data disk, установить Docker и поднять один демонстрационный MinIO. Установка прикладного стека не относится к IaaS-конфигурации этого задания.

## Почему используется декларативный подход

Конфигурация описывает желаемое состояние, а не последовательность команд создания ресурсов. Terraform сам строит зависимости: сначала создаёт сеть, затем подсеть и группу безопасности, после этого диски и VM. При повторном запуске он сравнивает конфигурацию с сохранённым состоянием и формирует только необходимые изменения.

Это полезнее набора ручных команд по следующим причинам:

- один и тот же стенд можно воспроизвести в другом folder, заменив входные значения;
- `terraform plan` показывает изменения до их применения;
- конфигурация проходит code review и хранит историю архитектурных изменений;
- параметры VM и дисков можно увеличить без переписывания всей конфигурации;
- ошибочно созданный стенд можно последовательно удалить;
- при развитии решения одиночную VM можно заменить модулем, instance group или несколькими доменными workspace.

Таким образом, IaC даёт воспроизводимость уже на небольшом стенде, а параметризация оставляет путь к масштабированию без необходимости сейчас оплачивать и обслуживать production-топологию.

## Ограничения

- Стенд не является отказоустойчивым и находится в одной зоне доступности.
- Динамический публичный IP изменится после пересоздания VM.
- Прерываемая VM может быть остановлена облаком.
- Данные на диске не резервируются.
- Медицинские и финансовые production-данные на стенд не загружаются.
- Перед запуском значение `admin_cidr` в `terraform.tfvars` необходимо заменить на реальный публичный IPv4 администратора с маской `/32`.
